# Протокол mase (сервер 0.3.0)

Документ описывает **текущее поведение** Go-сервера версии 0.3.0 вместе с его недостатками. Примеры кадров сняты с тестового сервера (коммит `2946546`, 2026-09-19); токены заменены на `<token>`, телефоны и имена вымышлены. То, что не проверялось запуском, помечено «по коду». Планируемый протокол v2 (подтверждения доставки, синхронизация, единая команда отправки) описан в `ROADMAP.md`, Фаза 7 — здесь его нет.

## 1. Транспорт

| Что | Значение |
|---|---|
| Основной канал | WebSocket, `GET /ws`, текстовые кадры, в каждом кадре один JSON-объект |
| Файлы | HTTP: `POST /upload`, `GET /media/<mediaId>` (см. раздел 6) |
| Проверка живости | `GET /health` → `200 ok` (всегда, базу не проверяет) |
| Размер кадра | до 512 КиБ (иначе соединение закрывается) |
| Keep-alive | сервер шлёт WebSocket-ping каждые 54 с, ждёт pong 60 с; клиент (OkHttp) отвечает сам. Прикладной `ping`/`pong` тоже есть, но приложение им не пользуется |
| Соединений на пользователя | **одно**: при входе с нового соединения прежнее закрывается (проверено, код закрытия 1005) |
| Тайм-аут неаутентифицированного сокета | нет |
| Ограничения частоты | нет |

Продовый адрес зашит в prod-сборку приложения (`wss://mase.nemilk.ru/ws`); dev-сборка ходит на `ws://<хост>:8081/ws`.

## 2. Формат кадров

Клиент → сервер: `{"type": "<тип>", "token": "<токен>", ...поля}`. Токен нужен во всех кадрах, кроме `auth.login` и `auth.register`. Приложение кладёт токен в **каждый** кадр.

Сервер → клиент: `{"type": "<тип>", ...поля}`. Ошибка: `{"type":"err","code":"<код>"}` (коды — раздел 5).

**Пользователь** (`user`; телефон и хеш пароля наружу не отдаются):

```json
{"id":1,"displayName":"Alice A","username":"alice","bio":"hi","avatarMediaId":""}
```

**Сообщение** (`message`), поля со знаком `?` присутствуют не всегда:

| Поле | Тип | Смысл |
|---|---|---|
| `id` | число | глобальный номер сообщения |
| `chatId` | число | чат; `1` — общий чат |
| `senderId` | число | автор |
| `otherUserId?` | число | только в «живых» событиях личных чатов: собеседник получателя события |
| `senderName?` | строка | только в «живых» событиях группы |
| `body` | строка | текст (у фото пустой) |
| `msgType` | строка | `text` или `photo` (в схеме предусмотрены также `voice`, `file`, но сервер их не создаёт) |
| `mediaId` | строка | имя файла на сервере, для текста пустая строка |
| `ts` | число | время создания, миллисекунды Unix |
| `status` | строка | `sent`; после квитанции в БД `read` (значения `delivered` сервер не выставляет) |
| `replyToId?` | число | ответ на сообщение |
| `editedAt?` | число | время правки, мс |
| `durationSec?` | число | длительность голосового, если > 0 |

В истории (`chat.history`) `otherUserId` и `senderName` **не передаются**, а удалённое сообщение приходит с пустым `body` и без признака удаления (проверено: флага `isDeleted` в JSON нет, остаются `status` и `editedAt`).

## 3. Аутентификация

Вход по телефону и паролю, SMS-кодов нет. Телефон — только строка длиной от 4 символов, он не проверяется и не нормализуется.

```text
-> {"type":"auth.register","phone":"+70000000001","password":"secret123","displayName":"Alice","username":"alice"}
<- {"type":"auth.session","token":"<token>","user":{"id":1,"displayName":"Alice","username":"alice","bio":"","avatarMediaId":""}}
<- {"type":"evt.presence","online":[1]}
```

- `auth.register`: пароль от 4 символов; пустой `username` заменяется на `u` + 7 цифр, `username` приводится к нижнему регистру; пустой `displayName` заменяется на `username`.
- `auth.login` (`phone`, `password`): при неверных данных `bad_credentials` (одинаково для неизвестного телефона и неверного пароля).
- `auth.resume` (`token` на верхнем уровне): возвращает тот же токен и пользователя; неизвестный токен → `session_expired` (токены на самом деле не истекают: срока жизни нет, отзыва тоже).
- Соединение считается аутентифицированным после первого кадра с действующим токеном; каждый новый успешный вход рассылает всем `evt.presence`.
- Каждый `auth.login` и `auth.register` выпускает **новый** токен; старые остаются действительными.

## 4. Сообщения клиента и ответы сервера

«Всем» в таблице означает **всем аутентифицированным пользователям**, а не участникам чата: так сервер работает сейчас (см. раздел 7).

### Профиль, друзья, поиск

| type | Поля | Ответ и рассылка |
|---|---|---|
| `ping` | — | `{"type":"pong"}` |
| `profile.update` | `displayName`, `username`, `bio` | `evt.profile` всем (включая автора); `username_taken` при занятом имени. Пустой `username` записывается как пустая строка |
| `profile.set_avatar` | `avatarMediaId` | `evt.profile` всем |
| `friends.add` | `friendUserId` | `friends.list` автору; существование пользователя не проверяется |
| `friends.list` | — | `{"type":"friends.list","friends":[user,…]}` |
| `user.lookup` | `username` или `userId` | `{"type":"user.lookup","user":user}` или `not_found` |
| `device.register_push` | `fcmToken` | ответа нет; токен хранится одним на пользователя, push пока заглушка |

### Чаты

| type | Поля | Ответ и рассылка |
|---|---|---|
| `chat.global.send` | `body` | `evt.message` (`chatId` 1) всем, включая автора. Пустое тело молча игнорируется |
| `chat.direct.open` | `peerUserId` | `{"type":"chat.open","chatId":2,"peer":user}`; `bad_peer`, `not_found` |
| `chat.direct.send` | `peerUserId`, `body`, `replyToId?` | `evt.message` автору (`otherUserId` = собеседник) и, если собеседник онлайн, ему (`otherUserId` = автор). Оффлайн-получатель ничего не получает (по коду): сообщение лишь лежит в БД |
| `chat.photo.send` | `peerUserId`, `mediaId`, `replyToId?` | как `chat.direct.send`, `msgType":"photo"`; `mediaId` не проверяется |
| `chat.history` | `chatId` | `{"type":"chat.history","chatId":N,"messages":[…]}`: последние 200 в хронологическом порядке, курсора нет. Общий чат открыт всем; для личного `forbidden` не участнику; **для группы всегда `forbidden`** (историю группы отдаёт `chat.group.open`) |
| `chat.receipt` | `messageId` | сообщение получает статус `read`; `{"type":"evt.receipt","messageId":2,"status":"read"}` всем, кроме автора запроса. Получатель и принадлежность сообщения не проверяются |
| `chat.message.edit` | `messageId`, `body` | БД меняется только для автора, но `{"type":"evt.message.edited","messageId":2,"body":"…","editedAt":…}` уходит **всем** в любом случае |
| `chat.message.delete` | `messageId` | тело очищается только у автора; `{"type":"evt.message.deleted","messageId":2}` всем в любом случае |
| `typing` | `chatId`, `isTyping` (**булево**) | `{"type":"evt.typing","userId":1,"chatId":2,"isTyping":true}` всем, кроме автора. Число вместо булева (так шлёт приложение) молча отбрасывается |

### Группы

| type | Поля | Ответ и рассылка |
|---|---|---|
| `chat.group.create` | `title`, `memberIds[]` | `chat.group.created` каждому участнику онлайн (включая создателя, он становится `admin`); пустое название → `bad_request` |
| `chat.group.send` | `chatId`, `body`, `replyToId?` | `evt.message` (с `senderName`) каждому участнику онлайн; не участнику `forbidden` |
| `chat.group.photo` | `chatId`, `mediaId`, `replyToId?` | то же, `msgType":"photo"` |
| `chat.group.open` | `chatId` | `chat.group.opened`, затем `chat.history` (в нём нет `senderName`) |
| `group.add_member` | `chatId`, `userId` | `group.member_added` всем участникам; **добавить может любой участник**, существование пользователя не проверяется |
| `group.leave` | `chatId` | `group.member_left` участникам, список берётся до удаления; **членство не проверяется** |
| `group.info` | `chatId` | `{"type":"group.info","chatId":3,"group":{…},"members":[user,…]}` |
| `group.list` | — | `{"type":"group.list","groups":[{"id":3,"title":"Team","avatarMediaId":"","createdBy":1}]}` |

Роли `admin`/`member` хранятся, но нигде не проверяются.

## 5. События сервера и коды ошибок

| type | Когда приходит |
|---|---|
| `auth.session` | ответ на `auth.login`, `auth.register`, `auth.resume` |
| `evt.presence` | при подключении и отключении любого пользователя: `{"type":"evt.presence","online":[1,2]}`. **`online` — массив чисел** (id), а приложение разбирает как массив объектов, поэтому список онлайн у него всегда пуст |
| `evt.profile`, `evt.message`, `evt.receipt`, `evt.message.edited`, `evt.message.deleted`, `evt.typing` | см. раздел 4 |
| `chat.open`, `chat.history`, `chat.group.created`, `chat.group.opened`, `group.info`, `group.list`, `group.member_added`, `group.member_left`, `friends.list`, `user.lookup`, `pong` | ответы и рассылки раздела 4 |
| `err` | ошибка, поле `code` |

| Код | Значение |
|---|---|
| `bad_json` | кадр не JSON |
| `auth_required` | кадр требует аутентификации, токена нет или он неверный |
| `bad_token` | `auth.resume` с пустым токеном |
| `session_expired` | `auth.resume` с неизвестным токеном |
| `bad_credentials` | неверный телефон или пароль |
| `phone_taken`, `username_taken` | занято при регистрации или смене профиля |
| `bad_request` | не прошла проверка полей (самый частый код) |
| `bad_dm`, `bad_peer` | неверные параметры личного чата |
| `forbidden` | пользователь не участник чата |
| `not_found` | пользователь или группа не найдены |
| `server_error` | сбой БД (в лог сервера пишется причина) |
| `unknown_type` | неизвестное значение `type` |

## 6. HTTP: файлы

Авторизация: заголовок `Authorization: Bearer <токен>` или параметр `?token=<токен>`. Ответы об ошибках: `{"error":"<код>"}`. Ответы содержат `Access-Control-Allow-Origin: *`.

| Запрос | Поведение |
|---|---|
| `POST /upload` | тело — сырые байты (тип файла определяется **по заголовку `Content-Type`**) или `multipart/form-data` с полем `file`; предел 100 МиБ, весь файл читается в память. Ответ `200 {"mediaId":"<32 hex>.<расширение>"}` |
| `GET /media/<mediaId>` | отдаёт файл (`http.ServeFile`, поддерживает `Range`); неизвестный файл → `404` с обычным текстом, имя с `/` или `..` → `400 bad_path` |
| `OPTIONS` | `200` для обоих путей |

Расширение выбирается по `Content-Type` клиента: `image/jpeg` → `.jpg`, `image/png`, `image/gif`, `image/webp`, `audio/ogg` и `audio/opus` → `.ogg`, `audio/mp4` и `audio/aac` → `.m4a`, `video/mp4`, `application/pdf`, всё остальное → `.bin`.

Коды: `401 unauthorized`, `405 method_not_allowed`, `400` (`parse_error`, `no_file`, `empty_body`, `bad_path`), `500 write_failed`.

## 7. Известные расхождения и дефекты

Проверено на тестовом сервере 2026-09-19, если не сказано «по коду». Подробности, ссылки на строки и способы исправления — `ROADMAP.md`, раздел 3.

| Что | Как проявляется |
|---|---|
| Правка, удаление, «печатает», квитанции и `group.leave` рассылаются **всем**, без проверки участия | посторонний пользователь получил новый текст чужого личного сообщения; подделка правки чужого сообщения дошла до автора и собеседника; `group.member_left` подделывается не участником (риски R-11…R-14) |
| Один пользователь — одно соединение | второй вход закрывает первый |
| Любой токен открывает любой файл | токен другого пользователя получил файл (`200`) |
| Тип файла берётся из заголовка клиента | байты «MZ…» (исполняемый файл) с `Content-Type: image/png` сохранены как `.png` |
| `typing` | приложение шлёт `1`, сервер ждёт `true`: событие теряется |
| `evt.presence` | формат не совпадает с разбором в приложении |
| Статусы | `delivered` не выставляется; приложение показывает `✓✓` только для него |
| История | нет курсора, только последние 200; для групп через `chat.history` — `forbidden`; в истории нет `senderName`, `otherUserId`, флага удаления |
| Доставка | оффлайн-получатель не получает ничего, сообщения не переотправляются, подтверждений доставки нет (по коду) |
| Токены | без срока жизни и отзыва; `session_expired` на деле означает «токен не найден» |
