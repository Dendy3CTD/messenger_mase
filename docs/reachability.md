### Замеры 2026-09-20 (записано со слов владельца, вывод netprobe в репозиторий не сохранён)

- **Контроль (локально):** все 8 шагов прошли, значит сервер и netprobe исправны, а не сервер виноват в зависании ниже.
- **Через Cloudflare из домашней сети:** `dns`, `tcp`, `ws`, `auth.register` и `ping` (малые кадры) прошли; на шаге «ws upstream 1 МБ» запись зависла. Примерно через минуту сервер записал `[HUB] user 1 disconnected` без данных, в журнале `cloudflared` — `Lost connection with the edge`.
- **Вывод владельца:** путь через Cloudflare режется уже на домашнем проводном интернете; для передачи медиа он непригоден. Остаётся оговорка карты (раздел 4.1): это **один прогон в одной сети**, оператор не записан, а требование Ф1 — три оператора × три пути. Для решения D1 нужны ещё замеры мобильных операторов и прямого пути.
- **Что зависание говорит о самом netprobe:** шаг завис, а не завершился ошибкой за 15 с, потому что у записи кадра не было дедлайна (запись блокировалась в буфере ядра). Исправлено (`tools/netprobe`, тест `TestPingFailsByDeadlineWhenPeerStopsReading`, без дедлайна он красный); при следующих прогонах зависший шаг завершится `FAIL` за 15 с. Это меняет только вид сбоя в отчёте, а не сам сбой.
- **Открытый вопрос:** какие именно кадры прошли. Один ping без отступа прошёл, кадр 256 КБ — нет; где между ними порог, не измерено. Для этого в netprobe добавлена лестница кадров 4, 16, 64, 128, 256 КБ (каждый размер — отдельная строка; общий объём к 256 КБ — 468 КБ). Читать результат так: срез на малом кадре — режет по размеру кадра; все кадры прошли, а «1 МБ» нет — режет по общему объёму (или по времени); срез на 256 КБ — порог между 128 и 256 КБ. Пока не прогонялась в реальных сетях.
