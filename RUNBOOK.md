## Прод-туннель поднялся случайно

**Когда применять.** Работают `cloudflared` или `mase-server`, а вы их не запускали; либо скрипт, тест или ошибочная команда могли их поднять. `mase.nemilk.ru` ведёт через туннель на порт 8080, значит всё, что слушает 8080, доступно снаружи.

**Чего боимся.**
1. Кто-то успел зарегистрироваться или написать, пока туннель был поднят.
2. Сервер открыл **живую БД** (`~/mase-data/mase.sqlite`) и что-то в ней изменил либо открыл **другую** БД, и живая оказалась не той, что ожидали.

**Правила.** Сначала улики, потом остановка. Ничего не удалять и не «чинить» до вывода. С БД работать только на **копии**: оригинал не открывать. Команды ниже проверены на тестовой БД.

### Шаг 1. Зафиксировать улики (до остановки, около минуты)

```bash
DATA="${MASE_DATA_DIR:-$HOME/mase-data}"
E="$DATA/incidents/$(date +%Y%m%d-%H%M%S)"; mkdir -p "$E"
{ date --iso-8601=seconds
  echo "== процессы cloudflared и mase-server (pid, ppid, время запуска, время работы, команда)"
  for d in /proc/[0-9]*; do            # ищем по имени исполняемого файла, а не по тексту команды
    exe="$(readlink "$d/exe" 2>/dev/null)"
    case "${exe##*/}" in cloudflared*|mase-server*)
      ps -o pid,ppid,lstart,etime,args -p "${d#/proc/}" | tail -n +2 ;;
    esac
  done
  echo "== слушающие порты 8080/8081"
  ss -ltnp 2>/dev/null | grep -E ':(8080|8081)\b'
} > "$E/processes.txt" 2>&1
for d in /proc/[0-9]*; do
  exe="$(readlink "$d/exe" 2>/dev/null)"
  case "${exe##*/}" in mase-server*)
    { echo "== pid ${d#/proc/}: $exe"
      tr '\0' '\n' < "$d/environ" | grep '^MASE_'
      ls -l "$d/fd" 2>/dev/null | grep -E 'sqlite'
    } >> "$E/server.txt" 2>&1 ;;
  esac
done
echo "улики сохранены в $E"; cat "$E/processes.txt" "$E/server.txt" 2>/dev/null
```

Что смотреть в выводе:
- `lstart` у `cloudflared` и у сервера — это **начало окна** (запишите как `START_TIME`, формат `ГГГГ-ММ-ДД ЧЧ:ММ:СС`);
- строки `-> …sqlite` — **какую БД сервер реально держал открытой** (главный факт: `MASE_DB` из окружения может отличаться от `-db` флага);
- если процессов нет, а порт 8080 занят чем-то ещё — остановитесь и разберитесь, чем именно.

### Шаг 2. Остановить (сначала туннель)

```bash
stop_by_exe() {   # $1 = шаблон basename исполняемого файла, $2 = название для сообщений
  local found=0 d exe
  for d in /proc/[0-9]*; do
    exe="$(readlink "$d/exe" 2>/dev/null)"
    case "${exe##*/}" in $1) echo "останавливаю $2: pid ${d#/proc/} ($exe)"; kill -TERM "${d#/proc/}"; found=1 ;; esac
  done
  [ "$found" = 1 ] || echo "$2: не запущен"
}
stop_by_exe 'cloudflared*' "туннель"     # 1) сначала туннель: закрывает доступ снаружи
sleep 2
stop_by_exe 'mase-server*' "сервер"      # 2) затем сервер
sleep 1
ss -ltn | grep -E ':(8080|8081)\b' && echo "ПОРТ ВСЁ ЕЩЁ ЗАНЯТ — проверьте процессы вручную" || echo "порты 8080/8081 свободны"
```

Окно инцидента: от `lstart` до момента остановки. Если туннель поднимался без сервера на 8080 (в шаге 1 нет `mase-server` и порт свободен), домен отвечал ошибкой Cloudflare и данных не было — переходите к шагу 3 только для порядка.

### Шаг 3. Быстрая проверка живой БД (БД не открываем)

```bash
DATA="${MASE_DATA_DIR:-$HOME/mase-data}"; cd "$DATA"
stat -c '%n  inode=%i  рождён=%w  изменён=%y  размер=%s' mase.sqlite mase.sqlite-wal
sha256sum mase.sqlite mase.sqlite-wal
```

Эталон живой БД `~/mase-data/` на **2026-09-20** (в ней 1 пользователь — пробный `netprobe`, `+70000000099`, 1 сессия, 0 сообщений; **эталон обновлён из-за пробного аккаунта**; снят при остановленном проде, `PRAGMA integrity_check` на копии пары файлов — `ok`):

| Файл | inode | Рождён | Размер | Изменён | SHA-256 |
|---|---|---|---|---|---|
| `mase.sqlite` | 4890703 | 2026-06-29 18:46:34 | 4096 | 2026-06-29 18:46:34 | `e3ba06536f7dbba337dee3c1c5f01b43660ce276abb54c5cee2d5defc5b970aa` — **не доказательство**, см. ниже |
| `mase.sqlite-wal` | 4890704 | 2026-06-29 18:46:34 | 152472 | 2026-09-20 17:48:47 | `a9dbe09e7657633673fac3b5435da70973e9901bcc0e1f2af85b99018c966131` |

Как читать:
- **Хеш основного файла `mase.sqlite` ничего не доказывает.** У БД в режиме WAL, пока не было контрольной точки, данные лежат в `-wal`, а основной файл — пустой заголовок; у любой свежесозданной пустой БД он побайтно такой же (проверено). Различают БД **`-wal` (размер, хеш, время изменения)** и **inode с временем рождения** файла.
- `mase.sqlite-shm` не использовать: он меняется даже когда БД просто открыли на чтение.
- Совпали `-wal` и inode с эталоном → в живую БД ничего не писали.
- Не совпали, или inode и «рождён» другие → живую БД открывали и меняли либо подменили; см. шаг 5.
- Эталон честен, только пока прод не работал легитимно после его снятия. **Обновляйте эталон** (строкой в конце раздела) после каждой плановой остановки прода, восстановления из копии или переноса файлов.
- Копировать БД нужно **парой** `mase.sqlite` + `mase.sqlite-wal`: копия одного основного файла теряет все данные.

### Шаг 4. Что произошло в окне (только на копии БД)

Сервер уже остановлен (шаг 2), поэтому копия согласована. Скрипт копирует файлы во временный каталог и читает копию; оригинал не открывается. Это копия **для чтения при разборе инцидента, а не резервная копия**: настоящие бэкапы делаются только средствами SQLite (`.backup`), копирование файлов живой БД для бэкапов запрещено (см. Ф2 в карте). Для другой БД, чем живая (шаг 1), задайте `DB=/путь/к/ней.sqlite`.

```bash
START_TIME='2026-09-19 21:36:00'   # из шага 1
inspect_window() {
  local DATA="${MASE_DATA_DIR:-$HOME/mase-data}" DB="${DB:-${MASE_DATA_DIR:-$HOME/mase-data}/mase.sqlite}" START C
  [ -n "${START_TIME:-}" ] || { echo "укажите начало окна: START_TIME='2026-09-19 21:36:00' (время запуска туннеля из шага 1)"; return 1; }
  START=$(date -d "$START_TIME" +%s) || { echo "не удалось разобрать START_TIME"; return 1; }
  [ -f "$DB" ] || { echo "нет файла $DB"; return 1; }
  C="$(mktemp -d)"; cp -p "$DB" "$C"/ || return 1
  [ -f "$DB-wal" ] && cp -p "$DB-wal" "$C"/          # данные могут лежать только в WAL — копируем обязательно
  python3 - "$C/$(basename "$DB")" "$START" <<'PY'
import sqlite3, sys
db, start = sys.argv[1], int(sys.argv[2])
c = sqlite3.connect(db)                                  # это копия; оригинал не открываем
def q(title, sql, args=()):
    try:
        rows = c.execute(sql, args).fetchall()
    except sqlite3.OperationalError as e:
        print(f"\n== {title}: таблицы нет ({e})"); return
    print(f"\n== {title}: {len(rows)}")
    for r in rows: print("  ", r)
print("целостность БД:", c.execute("PRAGMA integrity_check").fetchone()[0])
q("итого: пользователей, сообщений, макс. id пользователя, самая ранняя регистрация",
  "SELECT (SELECT count(*) FROM users), (SELECT count(*) FROM messages), (SELECT max(id) FROM users), "
  "(SELECT datetime(min(created_at),'unixepoch','localtime') FROM users)")
q("новые пользователи в окне (id, логин, когда)",
  "SELECT id, username, datetime(created_at,'unixepoch','localtime') FROM users WHERE created_at >= ? ORDER BY id", (start,))
q("новые сессии в окне (user_id, когда) — входы и регистрации",
  "SELECT user_id, datetime(created_at,'unixepoch','localtime') FROM tokens WHERE created_at >= ? ORDER BY created_at", (start,))
q("новые сообщения в окне (id, чат, отправитель, тип, когда)",
  "SELECT id, chat_id, sender_id, msg_type, datetime(ts/1000,'unixepoch','localtime') FROM messages WHERE ts >= ? * 1000 ORDER BY id", (start,))
q("новые группы в окне (id, создатель)",
  "SELECT id, created_by FROM groups WHERE created_at >= ?", (start,))
PY
  rm -rf "$C"
}
inspect_window
```

Файлы медиа, появившиеся в окне:

```bash
find "${MASE_MEDIA:-$HOME/mase-data/media}" -type f -newermt "$START_TIME" -printf '%TY-%Tm-%Td %TH:%TM  %s байт  %f\n'
```

Что показывает вывод: число пользователей и сообщений, самую раннюю регистрацию, новых пользователей, сессии (входы и регистрации), сообщения и группы за окно. Телефоны в вывод намеренно не выводятся.

### Шаг 6. То, что не видно на этой машине

- **Cloudflare.** В панели аккаунта проверьте, когда коннектор туннеля был подключён, и посмотрите аналитику по хосту `mase.nemilk.ru` за окно: были ли запросы и откуда. Названия разделов (Zero Trust → Networks → Tunnels, аналитика домена) я не проверяла и они могут отличаться.
- **Логи сервера.** Сейчас сервер пишет только в терминал, где его запускали: сохраните прокрутку. Строки `[AUTH] register OK …` содержат номер телефона — это личные данные, не публикуйте их. После Ф4 логи будут в journald без телефонов.

### Шаг 7. Закрыть инцидент

1. Записать в `docs/incidents/ГГГГ-ММ-ДД.md`: окно, какая БД была открыта, результат шагов 3–4, случай из таблицы, решение.
2. Обновить эталон (последняя строка журнала эталонов ниже), если БД менялась осознанно.
3. Запускать прод снова только после вывода, и только так, из интерактивного терминала: `MASE_I_MEAN_PROD=1 MASE_DB=~/mase-data/mase.sqlite ./go-server/deploy/run.sh prod` (переменную `MASE_I_MEAN_PROD` не экспортировать в окружение: скрипт без терминала и без неё прод не стартует).

### Ограничения этой проверки

- **Нет журнала доступа.** Видно только то, что осталось в БД: регистрации, сессии, сообщения, группы, файлы. Входы без записи, чтение и просмотр чужих данных (например, история общего чата и `user.lookup` доступны любому зарегистрированному) проверить нельзя.
- **Регистрация открыта** (инвайтов пока нет, Ф6), поэтому шаг 4 — главный источник ответа.
- **Push-токены и изменения профиля** не имеют времени в БД: шаг 4 их не покажет.
- Проверка достоверна, пока эталон свежий.

## Телефон не подключается к dev-серверу

Симптом: `run.sh dev` работает, на компьютере `curl http://127.0.0.1:8081/health` отвечает `ok`, а приложение Mase Dev на телефоне показывает «Нет соединения». Причина, найденная 2026-09-20: на машине `table inet filter`, `chain input` с `policy drop`; разрешены `lo`, `established/related` и `tcp dport 5555` из `192.168.0.0/16` (наследство C++-версии), порт 8081 закрыт.

Проверка (порядок важен, каждый шаг отсекает свою причину):

1. Сервер жив локально: `curl -s http://127.0.0.1:8081/health`. Не отвечает → проблема не в сети, смотрите вывод `run.sh dev`.
2. Сервер слушает не только loopback: `ss -ltn 'sport = :8081'` должен показать `*:8081` или `0.0.0.0:8081`, а не `127.0.0.1:8081`.
3. Адрес в приложении верный: сборка сделана с текущим IP машины (`hostname -I`, `MASE_DEV_HOST=<IP> ./build_apk.sh install-dev`). Если IP изменился (DHCP), пересоберите.
4. Телефон и машина в одной сети, изоляция клиентов на роутере выключена. Проверка: с телефона открыть в браузере `http://<IP>:8081/health`.
5. **Файрвол:** `sudo nft list ruleset`. Если в цепочке `input` стоит `policy drop` и нет правила для порта 8081, соединение молча отбрасывается. Временное правило только для локальной сети, как у 5555 (пропадёт после перезагрузки или перезагрузки `nftables`):

   ```bash
   sudo nft add rule inet filter input ip saddr 192.168.0.0/16 tcp dport 8081 accept
   ```

   После проверки убирайте временное правило (`sudo nft -a list chain inet filter input`, найти `# handle N`, `sudo nft delete rule inet filter input handle N`) или переносите его в `/etc/nftables.conf` осознанно (см. задачу в Ф4 карты).

Порт 8081 открывать только на время работы с dev и только для локальной сети; dev-сервер работает без TLS.

## Копии перед миграцией

Перед миграцией БД с данными сервер и `mase-server migrate up|down` сами делают копию `<БД>.pre-migrate-<из>-to-<в>-<время>.sqlite` (`VACUUM INTO`, права 600) рядом с БД и проверяют её `integrity_check`. Если копию сделать не удалось, миграция **не выполняется**, а в БД ничего не меняется. Для пустой БД и когда применять нечего, копий нет. Автоматически они не удаляются: удаляйте вручную, когда убедились, что миграция прошла (`ls <БД>.pre-migrate-*`). Это страховка до появления бэкапов Ф2, а не их замена: копия лежит на том же диске.

Откат к копии (сервер остановлен): `mv <БД> <БД>.broken; cp -a <БД>.pre-migrate-….sqlite <БД>; rm -f <БД>-wal <БД>-shm`. Копия целая, без `-wal`, поэтому копирование файла здесь допустимо.
